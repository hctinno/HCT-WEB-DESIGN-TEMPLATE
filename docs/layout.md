# 레이아웃 — 앱 셸 구조

## 왜 "페이지"가 아니라 "셸"인가

마케팅 사이트는 페이지마다 레이아웃이 다릅니다. 관리도구는 반대입니다.
고정된 껍데기 안에서 내용만 갈아끼웁니다. 노션·지라·슬랙이 모두 같은 구조를 쓰는 이유는,
사용자가 화면을 옮겨 다녀도 **탐색 위치와 조작 방법이 그대로 남기** 때문입니다.

그래서 이 시스템의 규칙 1번은 이것입니다: **모든 화면은 `AppShell` 안에 들어간다.**

## 영역별 역할

| 영역 | 역할 | 넣지 말아야 할 것 |
|---|---|---|
| 사이드바 | 어디로 갈 수 있는가 | 페이지별 액션 버튼 |
| 상단바 | 지금 어디에 있는가 + 전역 기능 | 페이지 제목 (PageHeader 와 중복) |
| 메인 | 지금 보는 내용 | 자체 헤더·자체 좌우 여백 |
| 우측 패널 | 선택한 항목의 상세 | 주 작업 흐름 |

## 화면 원형

### 1. 대시보드 (`src/pages/DashboardPage.jsx`)

```
PageHeader (제목 + 기간 선택 + 주 액션)
StatGrid   (KPI 3~4개)
ChartFrame (차트 2~3개, 2:1 비율 권장)
TableCard  (최근 항목 — 다음 행동으로 이어지는 목록)
```

대시보드는 "보기만 하는 화면"이 되면 안 됩니다. 항상 마지막에 **행동으로 이어지는
목록**을 두세요. 이상 징후를 발견했을 때 바로 클릭할 대상이 있어야 합니다.

### 2. 목록 + 상세 (`src/pages/ListPage.jsx`)

```
PageHeader (제목 + 생성 버튼)
Banner     (조건부 — 주의가 필요한 상태가 있을 때)
FilterBar  (검색 + 필터 + 적용된 필터 태그 + 밀도 전환)
TableCard
  └ TableToolbar → DataTable → TablePagination
RightPanel (행 선택 시 열림)
```

관리도구에서 가장 흔한 화면입니다. 핵심은 **행 클릭 → 우측 패널**입니다.
페이지를 전환하면 사용자는 목록에서의 스크롤 위치와 필터 맥락을 잃습니다.

### 3. 설정

좌측에 설정 카테고리 목록, 우측에 폼. 폼은 섹션별로 나누고 각 섹션마다 저장 버튼을
두는 것이 아니라, 변경 사항이 있을 때 하단에 저장 바를 띄우는 편이 낫습니다.

## 오버레이 선택 기준

| 상황 | 사용 | 이유 |
|---|---|---|
| 삭제 확인, 짧은 입력 | `ConfirmDialog` / `Modal` | 집중이 필요하고 되돌리기 어려움 |
| 상세 보기·편집 | `Drawer` | 목록 맥락 유지 |
| 상시 상세 패널 | `RightPanel` | 목록↔상세를 계속 오감 |

## 반응형

- **lg (1024px) 이상**: 사이드바 고정, 우측 패널 고정
- **lg 미만**: 사이드바는 오버레이, 우측 패널은 전체 화면

관리도구는 대부분 데스크톱에서 쓰입니다. 모바일에서 테이블을 억지로 카드로 바꾸기보다,
가로 스크롤을 허용하고 핵심 열만 보이게 하는 편이 실용적입니다.
