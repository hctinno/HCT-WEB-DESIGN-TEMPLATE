# 레이아웃 — 앱 셸 구조

## 왜 "페이지"가 아니라 "셸"인가

마케팅 사이트는 페이지마다 레이아웃이 다릅니다. 관리도구는 반대입니다.
고정된 껍데기 안에서 내용만 갈아끼웁니다. 노션·지라·슬랙이 모두 같은 구조를 쓰는 이유는,
사용자가 화면을 옮겨 다녀도 **탐색 위치와 조작 방법이 그대로 남기** 때문입니다.

그래서 이 시스템의 규칙 1번은 이것입니다: **모든 화면은 `AppShell` 안에 들어간다.**

## 영역별 역할

| 영역 | 역할 | 넣지 말아야 할 것 |
|---|---|---|
| 사이드바 | 어디로 갈 수 있는가 | 페이지별 액션 버튼 |
| 상단바 | 지금 어디에 있는가 + 전역 기능 | 페이지 제목 (PageHeader 와 중복) |
| 메인 | 지금 보는 내용 | 자체 헤더·자체 좌우 여백 |
| 우측 패널 | 선택한 항목의 상세 | 주 작업 흐름 |

## 화면 원형

### 1. 목록 + 뷰 + 상세 (`src/pages/ListPage.jsx`)

관리도구에서 가장 흔한 화면이고, 이 시스템의 중심입니다.

```
PageHeader   (제목 + 생성 버튼)
Banner       (조건부 — 주의가 필요한 상태가 있을 때, 그 조건으로 가는 버튼 포함)
GridCard
  ├ ViewTabs     저장된 뷰 탭 (+ 변경 시 저장/되돌리기)
  ├ QueryBar     검색 + 필터 빌더 + 적용된 조건 칩 + 질의문
  ├ GridToolbar  뷰 전환(표/보드) + 그룹핑 + 밀도
  ├ DataGrid  또는  BoardView
  └ GridPagination
RightPanel + ObjectDetail  (행 선택 시)
```

핵심은 **이 모든 것이 하나의 질의 객체 위에서 동작한다**는 점입니다.
뷰를 바꿔도, 그룹핑을 바꿔도, 상세를 열어도 같은 질의 결과를 보고 있습니다.

### 2. 대시보드 (`src/pages/DashboardPage.jsx`)

```
PageHeader   (제목 + 기간 선택)
Banner       (임계값을 넘긴 지표가 있을 때 — 바로 그리로 가는 버튼 포함)
MetricTile   (지표 3~4개, 각각 클릭 시 드릴다운)
Widget       (분해 — 차원 전환 가능, 각 조각이 드릴다운)
GridCard     (조치가 필요한 항목 — 대시보드의 끝은 항상 행동)
```

대시보드는 "보기만 하는 화면"이 되면 안 됩니다.
지표 → 분해 → 목록으로 이어지는 **좁혀 들어가는 경로**가 있어야 합니다.

### 3. 설정

좌측에 설정 카테고리, 우측에 폼. 섹션마다 저장 버튼을 두지 말고,
변경이 있을 때 하단에 저장 바를 띄우세요.

## 오버레이 선택 기준

| 상황 | 사용 | 이유 |
|---|---|---|
| 삭제 확인, 짧은 입력 | `ConfirmDialog` / `Modal` | 집중이 필요하고 되돌리기 어려움 |
| 상세 보기·편집 | `Drawer` | 목록 맥락 유지 |
| 상시 상세 패널 | `RightPanel` | 목록↔상세를 계속 오감 |

## 반응형

- **lg (1024px) 이상**: 사이드바 고정, 우측 패널 고정
- **lg 미만**: 사이드바는 오버레이, 우측 패널은 전체 화면

관리도구는 대부분 데스크톱에서 쓰입니다. 모바일에서 테이블을 억지로 카드로 바꾸기보다,
가로 스크롤을 허용하고 핵심 열만 보이게 하는 편이 실용적입니다.
